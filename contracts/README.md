# Glamtoon characters

Ten thousand characters, each drawn once and issued in two editions that differ
only in the colour behind them.

- **Blue is the genesis.** Exactly one per character, ten thousand in all, sold.
  The price opens at 0.01 ETH and steps up by 0.01 every two and a half thousand
  sold, so the last two and a half thousand cost 0.04.

  | tokens | price |
  |---|---|
  | 1 – 2,500 | 0.01 ETH |
  | 2,501 – 5,000 | 0.02 ETH |
  | 5,001 – 7,500 | 0.03 ETH |
  | 7,501 – 10,000 | 0.04 ETH |
- **Green is free.** Anyone can mint the next generation of any character for the
  cost of gas. Generation 1, then 2, then 3, without limit.

A blue can be bought for somebody else with `mintBlueFor`, and the change goes
back to whoever paid. Green has no such door: the one per character rule counts
the minter, so a third party minting for you would spend your slot without
asking. Gas can still be paid by somebody else there, through ERC-4337 or
EIP-7702, because both leave the collector as the caller. Both editions arrive
through `_safeMint`, so a smart wallet, or the delegate behind an EIP-7702
wallet, must answer `onERC721Received` to take one. Mainstream wallets do.

Character #1 is the same character in both. Only the background changes.

Immutable, ownerless, no proxy, no upgrade path, on OP Mainnet. Built on
OpenZeppelin v5. The five deployed addresses and the opening time of the sale
are in the [root README](../README.md).

**The art is pinned.** `IPFS_ROOT` and `ARWEAVE` at the top of `src/GlamToon.sol`
name the finished art, and [PROVENANCE.md](../PROVENANCE.md) records both and how
to put the files back at the same addresses if a pin ever lapses.

## Contracts

Two contracts to read.

| | What it is |
|---|---|
| `GlamToon.sol` | The ERC-721: the sale, the ids, the metadata, the art URLs. Immutable, and **has no owner at all**. |
| `Treasury.sol` | Where the money is paid. **The only contract with an owner.** |

Plus four generated files under `src/gen/` that nobody opens: `TraitData0.sol`
and `TraitData1.sol` hold the packed trait records, 5,000 characters each;
`TraitNames.sol` holds every category and value name; `TraitSchema.sol` holds the
record layout and the hashes of the other three. All are regenerated by one
script.

Secondary sales carry a 2% royalty, signalled through ERC-2981 and payable to
the treasury. It is fixed at construction like everything else in the token.

The two art identifiers, `IPFS_ROOT` and `ARWEAVE`, and the token page base,
`TOKEN_BASE`, are file-level constants at the top of `GlamToon.sol`. They sit at
file level rather than inside the contract so the deploy script can read them,
and on any chain but anvil it refuses a broadcast if one still says
`PLACEHOLDER` or does not have the shape it should.

## Token ids

    tokenId = generation * 10000 + imageId,  imageId in [0, 9999]

Characters are numbered **0 to 9999**, matching the art and the metadata the
pipeline produces. Generation 0 is the blue edition and takes ids 0 to 9999,
generation 1 takes 10000 to 19999, and so on upward. The image id is always the
last four digits and the generation is everything above them, so `30007` reads
directly as character 7, generation 3.

| | gen 0 | gen 1 | gen 2 | gen 3 |
|---|---|---|---|---|
| **character 0** | 0 | 10000 | 20000 | 30000 |
| **character 7** | 7 | 10007 | 20007 | 30007 |

Decoding is

```solidity
imageId    = tokenId % 10000;
generation = tokenId / 10000;
```

Zero based on purpose. A one based scheme needs a minus one on both sides and
still gets every multiple of 10000 wrong unless it is written carefully; this
has no offset anywhere, and the file path is `blue/{imageId}.png` with no
arithmetic between the contract and the art.

## No administrator

`GlamToon` has no `Ownable`, no proxy, no pause, no mint switch, and no setter
of any kind. The trait data, the payee and the royalty are fixed at construction
and there is no function that changes them. There is no burn.

It does expose an `owner()`. **That grants nothing here.** No modifier reads it,
no function checks it, and no behaviour of the token depends on it. It exists
because marketplaces such as OpenSea use `owner()` to decide who may edit a
collection page (banner, description, category), and a collection with no
`owner()` gives them nobody to ask. Inside the token it is a label, not a key.

Outside the token it can be more. Other contracts on OP read `owner()` and give
the address it names their own settings for the collection. The Royalty
Registry is one: it lets that address register a royalty override, so lookups
made through the registry can answer with a different royalty than
`royaltyInfo` does, and an override set before a handover stays set after it.

The label reads the treasury's owner rather than an address of its own, so
handing the treasury on moves it too. Each marketplace decides for itself when
it reads `owner()` again, so do not count on a collection page following a
handover. The treasury refuses to renounce, so the label can never point at
nobody. Only the current owner can start a handover, though: if that key is
lost, the label and the beneficiary are both fixed for good.

The money is the one thing that stays steerable, and it is steerable from outside:

    GlamToon   ──ETH──▶  Treasury  ──▶  beneficiary
    no owner              Ownable2Step   changeable
    fixed payee           owner may
                          repoint it

`GlamToon` names one payee and can never send anywhere else. `withdraw()` takes
no arguments and checks no caller: anyone may call it, and it can only ever reach
that one address. Redirecting the money is a treasury operation, never a change to
the token.

What the treasury owner key is worth: the ETH and tokens paid in, and every
future sweep, since it sets where sweeps go. It is also what `owner()` reports,
so it is the address a marketplace checks before letting anyone edit the
collection page, and the address contracts such as the Royalty Registry accept
settings from. It cannot mint, cannot change supply, cannot alter on-chain
metadata, and cannot touch anybody's NFT.

## The green edition: uncapped, but one each

Generations are uncapped. Anyone can keep taking the next generation of a
character for as long as people want them, so supply never locks anybody out.
The one thing that can is the minter's own wallet: one with code that does not
answer `onERC721Received` cannot take a green.

But **one address may take one green of a given character, ever**. Not one per
generation, one full stop. The same address can still take one green of each of
the other 9,999 characters, and can buy as many blues as it likes: the blue
edition is paid and unrestricted, and this rule never blocks it.

The record is of the mint, not of the holding, so sending the token away does
not free the slot. A balance check would be defeated in three steps: mint, move
it to a second wallet you control, mint again.

A determined script still defeats this with fresh wallets, so the total per
character remains unlimited. What the rule buys is that a collector minting by
hand cannot take the same character twice, at a cost of roughly 20,000 gas on
each free mint.

One consequence is worth stating plainly, because it is permanent: marketplaces
price a collection by one floor across every token in it. Green tokens are free
and pixel-identical across generations, so the floor shown next to the ten
thousand paid blues will sit at roughly the cost of gas. Rarity ranking does not
work on unbounded supply, and `totalSupply()` grows forever. None of that is a
safety problem, and it was chosen knowingly.

One cost is not about price. Wallets and marketplaces judge spam by contract,
not by token, and a free, uncapped edition that moves freely is what spam looks
like from outside: anybody can mint greens by the thousand from fresh addresses
and push them at wallets that never asked, for well under a dollar on OP. If a
classifier flags the contract, it hides the blues along with the greens, and
nothing on chain can undo that. The remedy is off chain: register the contract
as legitimate with the main spam lists before launch, and tell holders how to
add a hidden token by hand.

## Metadata

`tokenJSON(tokenId)` returns **plain JSON** and `tokenURI` adds one layer of base64
and the data-URI prefix. So a block explorer shows it as readable text, and from
a terminal it needs no base64 step:

```sh
cast call <nft> 'tokenJSON(uint256)(string)' 1 --rpc-url $OP_RPC | jq -r . | jq .
```

The `(string)` tells `cast` to decode the answer, which it prints as a quoted
string. `jq -r .` takes the quotes off and the second `jq` lays the JSON out.
Without the `(string)`, `cast` prints raw ABI hex and `jq` refuses it.

`tokenJSON` answers for any token id the collection can mint, minted or not, so
you can preview a character before buying it.

```json
{
  "name": "Glamtoon #7412 Gen 3",
  "description": "A Glamtoon character. 10,000 portraits, ages 18 to 70, in two inks.",
  "image": "ipfs://<ROOT>/green/7412.png",
  "external_url": "https://glamtoon.com/token/37412",
  "glamtoon": {
    "optimized": "ipfs://<ROOT>/green/7412.webp",
    "arweave": "ar://<MANIFEST>/green/7412.png",
    "arweave_optimized": "ar://<MANIFEST>/green/7412.webp",
    "image_id": 7412,
    "generation": 3
  },
  "attributes": [
    {"trait_type": "Edition",     "value": "Generation Green"},
    ... Dress Code, Age, Hair Cut, Hair Colour ...
    {"trait_type": "Generation",  "value": "3"}
  ]
}
```

### Why every attribute is a string

OpenSea will not rank a collection that carries **even one numeric trait**. Its
eligibility list reads "Only string traits (no numeric traits)", and the library
behind it, OpenRarity, refuses the whole collection rather than skipping the
offending trait:

```python
if collection.has_numeric_attribute:
    raise ValueError("OpenRarity currently does not support collections with "
                     "numeric or date traits")
```

So nothing here uses `display_type`. A numeric trait would still *render* — ENS
ships one and it works as a range box — but a single one costs the whole
collection its rarity rank, along with per-value floor prices and trait offers.

Generations 0 to 8 show their own value and everything from 9 upward shares the
label `9+`, so the filter row holds ten entries at most however long minting
runs. **Minting itself is never capped** — a holder's exact generation stays in
the token name, in the `glamtoon` object and on chain.

A single digit needs no padding, because a filter sidebar sorts values as text
and `10` would otherwise sort before `9`. The overflow label is built from the
threshold rather than written out, so the two cannot drift, and it has to sort
after every exact value: `9+` does.

Grouping the tail also stops the deepest generations being scored as the rarest
tokens, which is backwards. A late free mint is the least sought after, not the
most.

### Finding one character on a marketplace

There is no `Image` filter row, because ten thousand checkboxes would be unusable
and it would rank backwards: a popular character with many generations would hold
a *more common* image value and score lower than an unloved one.

The name carries it instead. Every generation of a character reads
`Glamtoon #7412`, `Glamtoon #7412 Gen 1`, and so on, and marketplace item
search matches on the name, so searching `7412` returns that character's whole
family. Ids stop at 9999, so no other id contains those four digits, and the
literal ` Gen ` stops a split id joining up to fake one. That is exact while
every generation stays below 1000. Generations are uncapped, and one of four
digits or more can contain the same four: `Glamtoon #5 Gen 7412` would match
too.

Characters below 1000 are less precise, since their number is a substring of
longer ids: searching `7` also matches `#17`, `#71`, `#700` and so on. Zero
padding the name would fix that, at the cost of no longer matching the metadata
the art pipeline writes. Left unpadded deliberately.

The image id is not an attribute at all. Ten thousand distinct values would make
a useless filter and would make every token unique on that axis, which wrecks the
rarity maths for the four traits that matter. It lives in the token id, the name,
and the `glamtoon` object instead.

The edition is not a stored trait either. It is a function of `generation == 0`,
so storing it would be ten thousand copies of a bit the token id already carries,
plus a way for the data and the picture to disagree.

Its values are written out in full, `Genesis Blue` and `Generation Green`, rather
than as the two colours. A buyer reading a filter list has no way to know that
`Blue` is the one per character that never comes again.

### A trait whose value is "None" is not written

Hair Colour carries a `None` value, and it is the only category that does. It is
how a character with no hair is written down: the record is a fixed sixteen bits
whatever the character, so something has to occupy those four, and `None` is that
something.

The attribute is not emitted. `_attributes` skips any value that reads `None`, so
those tokens carry five attributes where the rest carry six, and none of them
says a character has hair of no colour. A bald head has no hair colour, and the
rule this collection is built on is that nothing is declared that is not in the
picture.

The cost is that "characters with no hair" is not a filter. A marketplace lists
the values it observes, and this one is never observed. Hair Cut says `Short` for
those characters, which is where they sit on a length scale, so they are reachable
that way rather than as a category of their own.

### No provenance hash and no pre-reveal image

A provenance hash proves the art was not reshuffled after a blind mint. There is
no blind mint here: the buyer names the character they want, and the CID is
compiled in before anyone mints. The CID is the stronger commitment anyway, since
it covers filenames as well as bytes. Three more hashes, checked at deployment,
already pin the trait data.

A pre-reveal image exists to hide traits so nobody can snipe the rare ones. Picking
your character is the product here. It would also need an owner to flip the reveal,
which this contract does not have.

### Where the art lives, and what keeps it alive

The art is addressed by `ipfs://` and `ar://`, never a gateway host: a gateway is
a mutable name owned by one company.

Each character exists in two networks and two sizes. `image` is a single string
and can only name one of the four, and marketplaces read `image` and nothing else
— there is no standard "backup image" field in NFT metadata.

| | holds | getter | who reads it |
|---|---|---|---|
| `image` | full resolution PNG on IPFS | `imageURI` | every marketplace, wallet and indexer |
| `glamtoon.optimized` | lighter WebP on IPFS | `optimizedURI` | glamtoon.com only |
| `glamtoon.arweave` | full resolution PNG on Arweave | `arweaveURI` | glamtoon.com, and anyone who looks |
| `glamtoon.arweave_optimized` | lighter WebP on Arweave | `arweaveOptimizedURI` | glamtoon.com |

One getter per field, each taking the character and whether it is the genesis.
None of them takes a flag choosing which file to return, because a call reading
`(7412, true, false)` cannot be checked by eye.

Both IPFS fields hang off `ipfsRoot()` and both Arweave fields off
`arweaveManifest()`, and the two roots hold the same tree, so a path differs
only in its scheme.

The three extras sit under a made-up `glamtoon` key rather than at top level so
they can never collide with a name a marketplace reserves later. `image_data`,
`animation_url` and `background_color` are all real reserved keys and that list has
grown over time.

**`image` points at IPFS, deliberately.** `ipfs://` is the scheme every client
resolves, and a content-addressed CID never becomes *wrong* — only unresolved. If
pinning lapses, re-pinning the CAR file restores the identical CID, and the CAR can
itself be rebuilt byte for byte from the Arweave copy. [PROVENANCE.md](../PROVENANCE.md)
is the recipe.
Arweave is pay-once and needs nobody to remember anything, but `ar://` is handled by
fewer clients, and an image that will not render on a marketplace is a worse and
less fixable outcome than a pinning bill.

That choice is compiled in and cannot be changed, so the other half of it is
operational and **must** actually be done:

- pin to at least three independent services, plus a node you control
- archive the CAR file offline; it is the fastest way back to the CID, and the
  Arweave copy plus [PROVENANCE.md](../PROVENANCE.md) is the slower one

The CAR is about 24 GB, far past what a git host accepts, so it is not in this
repository. Nobody needs the archived copy to restore the art: PROVENANCE.md
rebuilds the same file, byte for byte, from the Arweave copy.

## Traits

Four categories bit-packed into 16 bits — two bytes per character, 20,000 bytes
across two data contracts of 5,000 characters each. A record never straddles a
chunk boundary.

Each category's value table is padded to exactly `2**bits` entries, unused slots
reading `-`. So **every index a record can hold names something**: `valueNames` is
total, there is no out-of-range trait to bounds-check, and metadata cannot be
bricked by one. The illegal state is unrepresentable rather than guarded against.

The data ships as plain Solidity `bytes constant`, not SSTORE2. It costs about 22%
more code, and buys three things: the chunks **verify on Etherscan as readable
source**, there is **no assembly in `src/` or `script/`**, and a wrong pointer
gives a clean revert instead of SSTORE2's unfixable out-of-gas. The deployed
system still runs assembly, all of it inside the OpenZeppelin libraries it uses,
such as Base64, Strings, the transient reentrancy guard, the receiver check, the
low level call behind every ether transfer, and SafeERC20.

The constructor asks each of the three data contracts for the hash of its own
bytes and compares the answer against constants generated alongside them, then
reads both sides of every chunk seam. A length probe would accept the right
contract carrying the wrong build; the hash check rejects an account with no
code, a different contract, a stale generation, and calldata a provider
truncated on the way in. It compares what each contract reports, so it trusts
the code answering. That is sound because the deploy script only ever passes
contracts it has just deployed from the generated source.

They are split because Ethereum caps a contract's code at 24,576 bytes (EIP-170),
OP keeps the same cap, and a `bytes constant` costs about a fifth again on top of
the bytes it holds. All 20,000 in one contract comes to 24,888, which does not
deploy; measured, the ceiling is 19,734 bytes of data. The two halves come to
12,738 and 12,771 bytes, with 11,838 and 11,805 to spare.

### Regenerating

Everything about traits comes from `scripts/characters/schema.json`. Edit it there
and nowhere else. The script needs `npm install` run once at the root of the
repository.

```sh
node ../scripts/characters/encode-traits.mjs            # regenerate from traits.csv
node ../scripts/characters/encode-traits.mjs --check    # fail if the generated sources are stale
```

A third flag, `--fixture`, writes a synthetic trait table over `traits.csv`
before regenerating. It was for the time before the real traits existed, and it
now refuses to run unless `--force` is passed as well, because the table it
would overwrite is the one that shipped.

`GlamToon.sol` is written against four categories in two chunks. Change the
category count in the schema and it stops compiling until it is updated to
match, which is the intended way to find out. The chunk count is only partly
caught that way: fewer than two stops compiling, but more than two still
compiles, and it is the constructor's seam reads that refuse it, so every
deployment and every test that deploys fails instead.

## Naming

Immutables are SCREAMING_SNAKE_CASE, because they are constants in practice and it
is worth seeing that at every use site: `PAYOUT`, `SALE_START`, `CHUNK0`,
`CHUNK1`, `NAMES`.

The one exception is `owner()`, which is lowercase because the name is an
interface rather than a choice. Marketplaces look up the selector for `owner()`
(`0x8da5cb5b`) to decide who may edit the collection page, and `OWNER()` would not
be found. It is written out as an explicit getter, which also lets it read the
treasury's owner rather than carrying an address of its own.

## What it costs

| | gas |
|---|---|
| buy a blue | 66k to 109k, 83k for a new wallet |
| take a green | 86k to 121k, 103k for a new wallet |
| `withdraw` | 34k |
| deploy the whole system | 9.7M |

These are transaction receipts from the build that ships, measured on a local
chain, so each includes the 21,000 every transaction pays. A mint costs more the
more storage it is first to write. The low end is a wallet that already holds a
Glamtoon, buying a blue whose word of the bitmap is already marked, or taking
the next generation of a character someone already has. The high end is a new
wallet: a blue bought as a gift with change, first in its word of the bitmap, or
the first green of a character. The very first blue and the very first green of
the whole collection each cost about 17k more, once, because each starts a
counter from zero: up to 126k and 138k.

`tokenURI` needs about 155k as a call, but it is a view and nobody pays for it.

A green mint still costs gas even though the token is free, and roughly 20k of
that gas is the price of OpenZeppelin over a gas-optimised ERC-721, which is the
trade this collection makes on purpose. On OP the gas is cheap: the L2 gas price
is a tiny fraction of a gwei, and the L1 data fee each transaction adds is
small, so the fee on a free mint is tiny. The table stays in gas because OP fees
move.

## Build and test

```sh
forge build
forge test
forge test --gas-report
```

Nothing in a checkout needs any environment at all. 695 tests across 39 suites,
in about a minute. Forge 1.8 and later run every invariant of a contract as one
campaign and report it once while all of them hold, so they print 663: the 38
invariants in six campaigns show as six results, each still checked on every
call. Among them: a full ten-thousand-token sellout that checks
every price against the rule; sweeps of all
ten thousand characters against the trait sheet, once for the packed records and
once for the metadata a marketplace would read, and the sheet itself checked row
by row against the art's own metadata; the bitmap asserted in both directions,
because one that reported everything as sold would otherwise pass; and the
compiled ABI of every contract held to a written list, so a function nobody
meant to add fails the tests.

Two suites read files that sit beside this directory, `../PROVENANCE.md` and
the art's metadata under `../metadata`, so the tests need the
whole repository and not `contracts/` lifted out by itself.

The invariant campaigns run with `fail_on_revert`, so a call the handlers did not
expect to fail stops the run instead of vanishing. Four of them start just below
a price step or near the sellout, because a campaign that starts from nothing
never gets past the first tier.

`forge coverage --ir-minimum` reports every function and every branch it counts
in `src/` as hit. The only lines it misses are the `return packed;` that closes
`record` in each chunk, which runs on every read but gets no bytecode of its own
in that build. For `script/Deploy.s.sol` it reports all thirteen functions; the
branches it misses are require arms that build cannot anchor, and a test drives
each of them to its own message, bar the `wrong schema` check, which compares two
constants. The flag is not optional: without it the instrumented build runs out
of stack in the metadata tests. Thirty three tests stand aside under coverage: the
gas assertions, two full metadata sweeps that run out of gas once instrumented,
the size limits, and the ABI checks, which read a build that coverage does not
write. Two more sweeps, `test_metadataForEveryCharacterInChunkZero` and
`test_metadataForEveryCharacterInChunkOne` in `TokenURI.t.sol`, run out of gas
the same way but are not marked to stand aside, so a coverage run ends by
reporting those two as failed. The coverage table is still written, and both
pass under `forge test`.

Symbolic proofs run under their own profile, with their own build directory so an
optimizer-off build can never poison the deploy build's cache:

```sh
FOUNDRY_PROFILE=halmos forge build
FOUNDRY_PROFILE=halmos halmos --function check_ --forge-build-out out-halmos \
  --solver-timeout-assertion 240000
```

Thirty six properties are proved rather than sampled, and a run has to report all
thirty six passed: halmos exits cleanly even when a suite it should have found is
missing. They cover the price at every point of the sale and none after the
sellout; a buyer charged the tier's price and refunded the rest, for every amount
and ceiling; a character never sold twice; nothing minted before the sale opens;
one green per address per character, generations in order, and never a green on a
blue id; ether leaving the token only for the treasury or as the caller's change,
for any one call anybody makes; no call clearing a green claim, a sold bit or the
royalty; the treasury moved only by its owner, with the label following it; and
the id packing as a bijection.

They have limits worth knowing. The packing proofs bound the generation below
2\*\*16, because division by a constant with a symbolic numerator is the known
hard case, and the unbounded range is fuzzed instead. Minters have no code, so
reentrancy is left to the attacker mocks in `test/unit`, and the deploy script does
not run. The halmos profile builds with the optimizer off and for cancun, which
puts the token past the 24,576 byte limit, so the proofs are about a program that
could not itself be deployed; the concrete tests run on the build that ships.

A second and larger symbolic suite, DinoSAT, lives in `test/dinosat` with a
profile and a build directory of its own, and a plain `forge test` leaves it
alone. It holds 222 properties. Halmos proved 214 of them, and the 8 it cannot
finish were fuzzed at a million runs each, with no counterexample to any.
[DINOSAT_REPORT.md](DINOSAT_REPORT.md) gives the threat model, every property,
what each proof assumes and the commands that reproduce the run, and
`dinosat-log.txt` is the result of that run, line by line.

The suite has been mutation-checked the hard way, twice. Three hundred and twenty
deliberate defects were compiled into `src/` and `script/` one at a time and the
whole suite run against each. Every one that changes what a caller can see is now
caught. The ones that survive change nothing observable, some of them only for the
data that ships: `continue` becoming `break` in `_attributes` is harmless while Hair
Colour, the last category, is the only one with a `None`, and narrowing the name
reader's upper bound changes nothing while the longest name is eleven bytes against
a thirty two byte slot. `test_noNameReachesTheEndOfItsSlot` pins that last reason,
so a regenerated table that fills a slot fails there instead of inheriting an
untested boundary.

## Deploy

The collection was deployed to OP Mainnet on 10 October 2026 with this runbook.
It stays here as the record of how that was done, and for anyone deploying a
fork of their own.

```sh
export DEPLOYER=0x...            # the address of the key that signs
export TREASURY_OWNER=$DEPLOYER  # holds the treasury until the Safe accepts it
export BENEFICIARY=0x...         # where sweeps should end up; if it is
                                 # $DEPLOYER, the owner must repoint it
export SALE_START=...            # unix seconds, when the sale opens, see below
export ALLOW_EOA_TREASURY_OWNER=true   # an ordinary wallet has no code
# export ALLOW_EOA_BENEFICIARY=true    # only for a plain wallet beneficiary
#                                      # other than $DEPLOYER, once checked
forge script script/Deploy.s.sol --rpc-url $OP_RPC --broadcast --verify --slow \
  --account glamtoon-deployer --sender $DEPLOYER
```

Import the deploying key once with `cast wallet import glamtoon-deployer
--interactive`, or sign with `--ledger` in place of `--account`. Never hand forge
the key as `--private-key` or export it: a command line is visible to every
process on the machine, and an exported key ends up in the shell's history.

`--slow` sends each transaction only once the one before it has confirmed and
succeeded, so a failure on chain stops the run rather than leaving the rest in
flight.

`--sender` is required with `--unlocked`, as in the rehearsal below: there forge
has no signer to take it from, so `msg.sender` falls back to forge-std's default
address. The script then simulates as an account nobody controls, which forge
funds for the simulation, so the balance guard passes and the run fails only
later, when forge replays the transactions against the chain. With a signer, as
above, forge takes the sender from the key, and `--sender` is the check
described under `TREASURY_OWNER` below.

**Pick `SALE_START` on purpose.** It is the moment the sale opens. On every
chain but anvil the script refuses a start less than an hour after the
deployment, and the constructor refuses one more than ninety days out. Until it
passes, both editions revert `NotStarted` for everybody, and that is when the
source is verified, the metadata read back and the treasury handed on, so leave
room for the Safe's signers too. `tokenJSON` answers for ids nobody owns yet, so
none of that needs a mint. The script measures the hour from the chain's latest
block when it simulates, so a value worked out from `date` long before the run
may already be too close.

Once the source is verified, anyone watching the chain can mint the moment the
sale opens. If everyone should start together, announce the address and the
opening time in advance, once step 5 below has read everything back. An
announcement made only after the sale opens leaves the first minutes to whoever
was watching.

**Make `TREASURY_OWNER` the address that signs the deployment**, as
`TREASURY_OWNER=$DEPLOYER` above does. The owner is the one input that can
repair another: it repoints a wrong beneficiary, and only it can hand the
treasury on. A wrong owner holds the treasury, the label and the say over every
sweep, and nothing can take them back. On OP Mainnet the script enforces this
for a plain wallet: an owner with no code has to be the signer, and no flag
changes that, because the signer is the one wallet the run proves somebody
holds the key to. To give the treasury to another plain wallet, deploy to your
own and hand it on with `transferOwnership`; the handover completes only when
the new owner signs `acceptOwnership`. A Safe, which has code, may be named
directly. The signer is the account forge runs the script from. Forge takes it
from the key and compares `--sender` with it, refusing to broadcast when the two
differ, so with both taken from `$DEPLOYER` the run is signed by the treasury's
owner.

The Safe guard is weaker than its message. With `ALLOW_EOA_TREASURY_OWNER`
exported, as above, a plain wallet passes only as the signer, so a mistyped one
is refused. Without it, any address with code passes: since Isthmus that includes an EIP-7702
wallet, which carries 23 bytes, and nothing checks that a contract is a Safe, or
that a Safe address copied from another chain belongs to you on OP. Before a Safe
takes the treasury, run `cast code`, `getOwners()` and `getThreshold()` against
it on OP.

`BENEFICIARY` has a guard of the same shape. An address with no code passes as
the signer, or with `ALLOW_EOA_BENEFICIARY` exported for a plain wallet you have
checked, and is refused otherwise. That refusal is what stops a Safe copied from
Ethereum that was never deployed on OP: it has no code here, it takes the proof
wei like any address, and nobody could spend a sweep sent to it. An address with
code passes, so read a Safe beneficiary back the same way.

Until the treasury is handed on, whoever holds the deploying key holds all of it:
the balance, every sweep, the `owner()` label and whatever that label controls
elsewhere. So hand it to the Safe before `SALE_START`, as step 5 below does. The
token never changes, and `owner()` follows because it reads the treasury.

The deploying key stays the creator of all five contracts for good, whatever
happens to the treasury. Block explorers let a contract's creator edit its token
profile, so claim the profiles with that key once the source is verified, and
keep the key as carefully as the Safe's.

Dry-run against a fork, not a bare simulation: with no RPC, `block.timestamp` is 1
and any realistic `SALE_START` trips the constructor's ninety-day bound.

### The order on the day

1. Rehearse against a fork of OP Mainnet, which costs nothing and exercises the
   real chain id, the real balance guard, the art guards and the hour's lead.
   The fork can act as the deployer, so no key is needed:

   ```sh
   anvil --fork-url $OP_RPC --port 8545 &
   cast rpc anvil_impersonateAccount $DEPLOYER --rpc-url http://127.0.0.1:8545
   forge script script/Deploy.s.sol --rpc-url http://127.0.0.1:8545 --broadcast \
     --slow --unlocked --sender $DEPLOYER
   ```

   A fork carries chain id 10, so nothing is skipped. Move its clock past
   `SALE_START` with `cast rpc evm_increaseTime` and `cast rpc evm_mine`, mint one
   of each, and read the metadata back before you spend anything real.
2. Deploy to OP Mainnet with the command above, and keep the addresses the run
   prints. If the run stops on its last transaction, the proof `sweep`, with
   `NothingToSweep`, read the treasury's balance before doing anything else. At
   zero, somebody else swept the proof wei to the beneficiary first and the
   deployment is complete. Deploying again would only leave a second token that
   nothing can stop.
3. Wait for verification on Optimistic Etherscan, or run `forge verify-contract`
   for anything that did not verify. Until the source is published, nobody can
   read what they are buying.
4. Read the chain back, not the script's output:
   `cast call <nft> 'tokenJSON(uint256)(string)' 0 --rpc-url $OP_RPC | jq -r . | jq .`,
   then open every URL it returns. Check `PAYOUT()`, `SALE_START()`, `owner()`,
   and the treasury's `owner()` and `beneficiary()`. Compare `SALE_START()` with
   the timestamp of the block that created the token: the script measured the
   hour's lead in its simulation, and the constructor takes any start up to
   ninety days out, a past one included. The Royalty Registry at
   `0x3D1151dc590ebF5C04501a7d4E1f8921546774eA` must answer
   `getRoyaltyLookupAddress(<nft>)` with the token itself.
5. Hand the treasury to the Safe: `transferOwnership(<safe>)` from the deployer,
   then `acceptOwnership()` from the Safe. If `BENEFICIARY` is the deployer, the
   Safe then calls `setBeneficiary` with the address sweeps should end up at;
   until it does, anybody can sweep the treasury to the deploying key. Then
   read it all back:

   ```sh
   cast call <treasury> 'owner()(address)' --rpc-url $OP_RPC         # the Safe
   cast call <treasury> 'pendingOwner()(address)' --rpc-url $OP_RPC  # zero
   cast call <nft> 'owner()(address)' --rpc-url $OP_RPC              # the Safe
   cast call <treasury> 'beneficiary()(address)' --rpc-url $OP_RPC   # where sweeps go
   cast call 0x3D1151dc590ebF5C04501a7d4E1f8921546774eA \
     'getRoyaltyLookupAddress(address)(address)' <nft> --rpc-url $OP_RPC
   ```

   The Royalty Registry must still answer with the token itself. It is asked
   again because an override registered while the deployer held the label
   survives the handover. A wrong beneficiary is the Safe's to repoint. If any
   other read is wrong, abandon this deployment and deploy again before
   `SALE_START`: nothing can stop the abandoned token, which still opens at its
   own `SALE_START`, so publish only the new address. Steps 3 to 5 all happen
   before `SALE_START`.
6. Once the sale opens, mint one blue and one green from a wallet that is not the
   deployer, and look at them on a marketplace.
7. Publish the token's address. If the opening was not announced in advance,
   announce it now, knowing that whoever watched the chain could mint from
   `SALE_START` on.

The script runs on OP Mainnet and a local anvil, and nowhere else: Ethereum
mainnet and every testnet are refused, because a chain id that looks right is the
easiest way to deploy to the wrong one. **OP Mainnet runs the art guards, the
balance floor, the hour's lead and the address guards**, and a fork of it carries the same chain id,
so the rehearsal exercises the real checks rather than tiptoeing round them. A bare anvil, with chain id 31337, is the only
place placeholders pass and the only place a sale may open on the deployment
block, which is what local development wants.

It also sweeps the constructor's one wei from the treasury to the beneficiary as
a real transaction. That proves the beneficiary takes ether, the second hop and
the one nobody checks. It does not prove the address is the right one, and
`sweep()` is callable by anyone, so until the owner repoints a mistyped
`BENEFICIARY`, the first bot to call it sends whatever the treasury holds there.

Two things the script cannot do, so do them by hand. Its assertions run in
simulation, before any transaction is sent, so they check the logic rather than
the mainnet result: re-read the deployed addresses afterwards. And the assertion
that the deployed art root matches the compiled one compares a constant to
itself, so it is the placeholder and shape guards that do the real work there.
Never pass `--resume`: every guard lives inside `run()`, and a resumed broadcast
skips all of them. It also replays the transactions the stopped run saved, the
token's `SALE_START` among them, so a run resumed late can land a token whose
sale is already open. If a run stops before the token is deployed, start again
from the beginning: the contracts it left behind do nothing without a token
pointing at them.

The script pins the chain, refuses placeholder art identifiers, deploys the data
before anything that checks its hash, and re-asserts every identity constant and
every wiring pointer after the deployment calls, still inside the simulation.
The token constructor is sent one wei so a payee that cannot receive ether fails
the deployment, once, rather than every withdraw forever.

**Before announcing anything, look.**
`cast call <nft> 'tokenJSON(uint256)(string)' 1 --rpc-url $OP_RPC | jq -r . | jq .`,
then open the URLs it returns. Rehearse the whole run on a fork of OP Mainnet
first: once the token contract is on OP Mainnet the trait data is pinned to it
forever.

The `bytes32` hashes in the verified `TraitSchema.sol` name the data this build
was generated against, and anyone can call `dataHash()` on a chunk and compare.
That answer comes from the chunk's own code, though, so it is only proof once the
chunk's source is verified too, or its runtime codehash matches the one this
build produces.

## How the art was pinned

Nothing about the contract logic changed. These are the steps that were taken,
in the order to follow if they ever have to be taken again.

1. The real categories, bit widths and value names went into `schema.json`, and
   the real trait table into `test/fixtures/traits.csv`.
2. The art was laid out as [PROVENANCE.md](../PROVENANCE.md) describes, with
   only `blue/` and `green/` in the folder, and packed into one CAR with
   `npx --yes ipfs-car@3.1.0 pack glamtoon --no-wrap --output glamtoon.car`. Its
   root was taken as `IPFS_ROOT`, and the CAR itself uploaded so every service
   reports that same root. The CID is a function of the tool, its version and the
   layout, so any other tool or flag produces a different CID and the compiled one
   goes dark. Without `--output` the CAR goes to standard output with no root in
   its header, so it fails both checks PROVENANCE.md makes before an upload.
   PROVENANCE.md records this recipe and the CAR's hash.
3. The same files went to Arweave under a path manifest. The manifest id is only
   knowable once every file's id is, so Arweave was complete and confirmed
   **before** any of this was compiled.
4. The identifiers went in at the top of `GlamToon.sol`.
5. `node ../scripts/characters/encode-traits.mjs`, then `forge test`. The suite
   checks the on-chain bytes against the encoder's own output, so a mismatch
   fails here.

Keeping the art reachable does not end there. Pin to at least three independent
services plus a node you control, and archive the CAR. Before deploying, and
after any change of pinning service, check all 40,000 paths on every store with
`scripts/verify-pin.mjs`, once per extension, as
[PROVENANCE.md](../PROVENANCE.md) shows: each IPFS service through its own
gateway, and Arweave with the manifest as `--cid` and an Arweave gateway such as
`https://arweave.net/` as `--gateway`. The script does not retry a 404, and an
Arweave gateway may answer one for a file it has not fetched before, so run a
failing Arweave check again before calling a file missing.

The script builds each path itself, as `blue/7412.png` with no padding, so
confirm that shape once against the contract. On the rehearsal fork,

```sh
cast call <nft> 'imageURI(uint256,bool)(string)' 7412 true \
  --rpc-url http://127.0.0.1:8545
```

must answer with a URI ending in `/blue/7412.png`. That one call is what
stops the script checking `/blue/7412.png` while the contract serves
`/blue/07412.png`.
